# Windows Installation — Support Runbook

**Audience:** the support engineer deploying `odoo-mcp-multi` on a client's
Windows machine (manual, one-machine-at-a-time rollout). Ping: **@sabrinavx**.

This page is a literal, copy-paste runbook. It documents the two errors you
**will** hit on a fresh Windows machine, why they happen, and the exact steps
to get past them. Follow it top to bottom.

> **Scope for now:** manual `pipx` install per machine. A signed, double-click
> installer is *planned but not built yet* — see
> [Why This Is Hard](#why-this-is-hard-rationale) at the bottom before
> promising a client a "next-next-next" experience.

## What You Are Installing

- **Python** — the runtime `odoo-mcp` needs.
- **pipx** — installs `odoo-mcp` into its own isolated environment.
- **odoo-mcp-multi** — the MCP server the AI client talks to.

The end state: the client's AI tool (Claude Desktop, Antigravity, Cursor, or
VS Code) can create records and pull HTML reports from Odoo.

## Prerequisites

- Windows 10 (21H1 or newer) or Windows 11.
- A local user account with **administrator** rights (needed only once, to
  clear the Smart App Control block in Step 4).
- The Odoo URL, database name, and the credentials or API key for the profile
  you will configure.

## Step 1 — Install Python

Open **PowerShell** (no admin needed) and run:

```powershell
winget install Python.Python.3.12
```

When it finishes, **close the window**. `winget` edited the `PATH`, and that
change only applies to a *new* terminal session.

## Step 2 — "pip is not recognized" (expected)

Open a **new** PowerShell window and check the tools:

```powershell
py --version
where.exe pip
```

You will very likely see this — it is **normal**, not a broken install:

```text
pip : El termino 'pip' no se reconoce como nombre de un cmdlet, funcion,
archivo de script o programa ejecutable.
```

(English locale: `pip is not recognized as an internal or external command`.)

**Cause:** Python installed, but its `Scripts\` folder is not on the `PATH` of
this session. Do **not** try to fix `PATH` by hand. Use the `py` launcher
instead — it lives in `C:\Windows\` (always on `PATH`) and never has this
problem:

```powershell
py -m pip --version
```

That command works. From here on, prefer `py -m pip` and `py -m pipx` over the
bare `pip` / `pipx` names.

> **If typing `python` opens the Microsoft Store:** turn off the fake aliases.
> Go to **Settings → Apps → Advanced app settings → App execution aliases** and
> switch **off** `python.exe` and `python3.exe`.

## Step 3 — Install pipx (user scope)

```powershell
py -m pip install --user pipx
py -m pipx ensurepath
```

`ensurepath` adds `%USERPROFILE%\.local\bin` to your user `PATH` — that is where
the `odoo-mcp` command will end up. **Close the window** so the new `PATH`
takes effect.

## Step 4 — The Device Guard / Smart App Control block

Open a **new** PowerShell window and install the package:

```powershell
py -m pipx install odoo-mcp-multi
odoo-mcp add-profile
```

On a fresh Windows 11 machine, `odoo-mcp` will very likely be blocked with this
message:

```text
C:\Users\<user>\.local\bin\odoo-mcp.exe ha sido bloqueado por la directiva de
Device Guard de su organizacion. Pongase en contacto con el personal de
soporte tecnico para obtener mas informacion.
```

**Cause:** the machine is **not** actually managed by an "organization". On an
unmanaged Windows 11 machine this message comes from **Smart App Control**, a
feature built on top of WDAC that blocks **unsigned** executables. The
`odoo-mcp.exe` file is a launcher *generated by pipx on the spot* — it is
unsigned and lives in a user-writable folder, which is exactly the profile
Smart App Control rejects. (Python itself ran fine because it is signed.)

You have two ways forward. Pick one.

### Option A (recommended for the 1x1 manual rollout) — turn off Smart App Control

Do this as **administrator**, once, on the client's machine:

1. Open **Windows Security**.
2. Go to **App & browser control**.
3. Click **Smart App Control settings**.
4. Set it to **Off**.

> **One-way switch — read before you click.** Once Smart App Control is set to
> **Off**, it **cannot be turned back on** without reinstalling Windows. You are
> permanently lowering that machine's protection. This is acceptable for a
> dedicated, single-purpose operator machine, but confirm with the client that
> they accept it before flipping it.

After turning it off, re-run:

```powershell
odoo-mcp add-profile
```

The command now works, and the rest of this runbook uses the plain `odoo-mcp`
command.

### Option B (no security change) — run through the Python module

If the client will **not** disable Smart App Control, you do not need the
blocked `.exe` at all. Run the tool as a Python module instead — the signed
Python interpreter is allowed:

```powershell
py -m odoo_mcp_multi add-profile
py -m odoo_mcp_multi run
```

`py -m odoo_mcp_multi <command>` does exactly what `odoo-mcp <command>` does.
When you use Option B, substitute it everywhere this runbook says `odoo-mcp`,
and use the Option B variant of the MCP client config in Step 6.

## Step 5 — Configure a Profile

Run the interactive wizard and answer the prompts (URL, database, auth):

```powershell
odoo-mcp add-profile
```

Non-interactive equivalents, if you already have the values:

```powershell
# Odoo < 19 (user + password)
odoo-mcp add-profile --name prod --url https://odoo.example.com --database mydb --user admin --password secret

# Odoo 19+ (API key)
odoo-mcp add-profile --name prod --url https://odoo.example.com --database mydb --api-key YOUR_KEY
```

The profile is written to `%USERPROFILE%\.config\odoo-mcp\profiles.json`.

> **Security note — credentials are not permission-locked on Windows.** On
> Linux and macOS this file is created with `600` (owner-only) permissions. On
> Windows that step is silently ignored, so the file is readable by any account
> on the machine. Make sure the operator's account is the only account on that
> machine, and never copy this file between machines — each machine should run
> its own `add-profile` with its own credentials.

## Step 6 — Wire It Into the AI Client

Add one server block to the client's MCP config file. Paths per client:

| Client | Config file path (Windows) |
| --- | --- |
| Antigravity | `%USERPROFILE%\.gemini\antigravity\mcp_config.json` |
| Claude Desktop | `%APPDATA%\Claude\claude_desktop_config.json` |
| Cursor | `.cursor\mcp.json` (project root) |
| VS Code | `.vscode\mcp.json` (project root) |

If you used **Option A** (Smart App Control off), use the plain command:

```json
{
  "mcpServers": {
    "odoo": {
      "command": "odoo-mcp",
      "args": ["run"]
    }
  }
}
```

If you used **Option B** (module fallback), point the client at Python instead:

```json
{
  "mcpServers": {
    "odoo": {
      "command": "py",
      "args": ["-m", "odoo_mcp_multi", "run"]
    }
  }
}
```

> If the client cannot find `py`, use the absolute path `C:\Windows\py.exe` as
> the `command`.

Restart the AI client after saving the file.

## Step 7 — Install the Agent Skills

The bundled skills teach the AI client how to drive Odoo (reports, record
creation). Install them for the client the operator uses — for example
Antigravity:

```powershell
odoo-mcp plugins install antigravity
```

Supported targets: `antigravity`, `agy`, `codex`, `opencode`, `kimi`,
`hermes`, `agents`. With **Option B**, run
`py -m odoo_mcp_multi plugins install antigravity` instead.

For **Claude Code** do not copy skills — install the plugin from the
Vauxoo AI marketplace instead (it bundles the skills and registers the
MCP server):

```text
/plugin marketplace add https://git.vauxoo.com/ai/marketplace.git
/plugin install odoo-mcp@vauxoo-ai
```

## Step 8 — Verify

```powershell
odoo-mcp list-profiles
odoo-mcp run
```

`list-profiles` should show the profile you created. `run` should start the
server and wait (no error, no immediate exit). Press `Ctrl+C` to stop the
manual test — the AI client will start it on its own.

Then, inside the AI client, ask it to pull a simple report or list a few
partners to confirm the end-to-end path works.

## Troubleshooting Quick Table

| Symptom | Cause | Fix |
| --- | --- | --- |
| `pip is not recognized` | `Scripts\` not on `PATH` | Use `py -m pip` (Step 2) |
| Typing `python` opens the Store | App execution aliases | Turn off the `python.exe` aliases (Step 2) |
| `odoo-mcp.exe ... blocked by Device Guard` | Smart App Control blocks the unsigned shim | Option A or Option B (Step 4) |
| `odoo-mcp` still not found after install | New `PATH` not loaded | Close and reopen PowerShell |
| Client shows the server but it never connects | Wrong `command` in config | Match Step 6 to the option you chose |

## Uninstall / Cleanup

```powershell
py -m pipx uninstall odoo-mcp-multi
```

Credentials are **not** removed automatically. Delete them by hand if needed:

```powershell
del "%USERPROFILE%\.config\odoo-mcp\profiles.json"
```

## Why This Is Hard (Rationale)

This section is for the team, not for the operator. It explains *why* a Python
CLI needs a whole runbook on Windows, and what a real fix looks like.

The Windows friction comes from three facts stacking up:

1. **The `odoo-mcp.exe` launcher is unsigned.** We do not ship it. `pipx`
   generates it locally from the package entry point at install time, so it is
   born without an Authenticode signature.
2. **It installs into a user-writable folder** (`%USERPROFILE%\.local\bin`).
   That is precisely the location application-control policies distrust.
3. **Smart App Control is on by default on Windows 11** and blocks unsigned
   code by reputation. The other two facts guarantee a block.

On top of that, `os.chmod` is a no-op on Windows, so the `600` permission we set
on `profiles.json` everywhere else does not apply — the credential file is left
world-readable on the machine.

None of this is a bug in the package. It is the expected outcome of shipping an
unsigned, pip-installed CLI onto a locked-down consumer OS.

## The Long-Term Fix (Planned, Not Built)

Clients increasingly require this to "just work" on Windows. The real project
is **not** "make an `.exe`" — an unsigned installer hits the *same* Smart App
Control block. The load-bearing piece is **code signing**. Planned tiers, in
order of value:

1. **Package the server with PyInstaller** into a single `.exe` that embeds
   Python. This removes the `PATH` / `pip` / `pipx` friction entirely.
2. **Wrap it in a real installer** (Inno Setup or MSI) that installs into
   `C:\Program Files\` (a non-user-writable, trusted location), registers in
   *Add/Remove Programs*, and — the highest-value part — **writes the MCP
   client config automatically**.
3. **Sign the `.exe` and the installer in CI** with an Authenticode
   certificate (OV builds reputation over time; EV gives instant SmartScreen
   trust). This is the step that actually clears Smart App Control and
   SmartScreen, and makes a true double-click install possible.

Infrastructure implication: the current CI runs on a Linux image
(`python:3.12-slim`) and **cannot** build a Windows `.exe`. This effort needs a
**Windows CI runner** (or `osslsigncode` for signing from Linux) plus a
purchased code-signing certificate — that runner is the heaviest new piece,
more than the packaging itself.

## Known Limitations (Validate With the Team)

- [ ] **Smart App Control off is irreversible.** Confirm clients accept a
  permanent protection downgrade on operator machines, or standardize on
  Option B (module fallback) instead.
- [ ] **`profiles.json` is world-readable on Windows.** Decide whether we need
  a Windows-specific ACL step, or accept it on single-user machines.
- [ ] **Option B changes the client config** (`command: py`). Confirm every
  target AI client resolves `py` / `C:\Windows\py.exe` correctly.
- [ ] **No signed installer exists yet.** Set expectations with clients who ask
  for a mandatory Windows package until the tiers above are built.
- [ ] **CI cannot build Windows artifacts today.** A Windows runner and a
  code-signing certificate are budget/procurement items to approve first.
